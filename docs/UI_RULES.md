# UI 規範（qa-knowledge 前端）

給自己（AI）改 `scripts/app.js` / `scripts/build.js` / `scripts/style.css` 前對照用。三條規則各自對應一次實際踩過的 bug，不是憑空立的規矩。

## 1. 連結一律用 `A()` helper，不寫行內 style

**規則**：任何可點擊連結都用 `app.js` 頂部的 `A(act, extra, txt, cls)` 產生，統一輸出 `class="lnk ' + (cls||'') + '"`。**禁止**在連結上另外寫 `style="text-decoration:..."` 之類的行內樣式。

**為什麼**：行內 `style` 的優先級高於任何外部 CSS，包含 `:hover`。2026-09-16 曾經在 `A()` 裡寫死 `style="cursor:pointer;text-decoration:none"`，導致外部無論怎麼加 `a:hover{text-decoration:underline}` 都沒用——索引頁節點連結、上一個/下一個導覽、首頁「最需要回頭看」清單全部因此完全沒有 hover 回饋，而且是同一個函式產生的連結全部一起中招，只能一次抓出來、改掉行內樣式的根源。

**檢查法**：`grep 'style="' scripts/app.js` 抓有沒有新的行內樣式偷跑進來，尤其是 `text-decoration`、`color`、`cursor` 這幾個外部 CSS 常見會管的屬性。

## 2. 每個可點擊元件要過一次互動狀態檢查清單

**規則**：新增一個可點的東西（連結、按鈕、自訂控制項）時，至少確認這四個狀態都有明確表現，不能只顧 default：

| 狀態 | 檢查什麼 |
|---|---|
| default | 看得出「這是可以點的」（游標、顏色，不需要底線但要有區別於純文字的視覺線索） |
| hover | 滑過去要有變化（顏色/背景/底線任一種都可以，但要有；純文字連結沒有其他裝飾時，底線是最低限度） |
| focus | 鍵盤 tab 到這裡要看得見焦點框（瀏覽器預設的 outline 不要用 `outline:none` 清掉，除非另外補一個更明顯的） |
| disabled | 按鈕型控制項若有「還不能按」的情境（例如知識檢測的提交按鈕），disabled 狀態要跟可按狀態有明顯差異（不能只靠滑鼠游標變化） |

**不用特別做**：active（按下瞬間）、loading——這個網站沒有真的網路請求會轉圈，除非之後真的加了才需要。

**為什麼**：2026-09-16 用真實滑鼠 hover（不是合成 `dispatchEvent`，那個測不出真的 `:hover`）逐一測過全站才發現至少 5 處完全沒有 hover：logo/品牌區塊、索引頁節點連結、節點頁上一個/下一個、節點頁頂部主題名稱、首頁弱點清單。這些全部是「加功能的當下沒有順手檢查互動狀態」累積出來的，不是單一次的疏忽。

**檢查法**：改完用滑鼠實際移過去看（不要用 JS 合成事件測，測不出真的 `:hover` pseudo-class），或至少對照 `scripts/smoketest.js` 有沒有涵蓋到這個新元件。

## 3. 新增 `sticky` / `fixed` 元素前，先想清楚捲動時的視覺關係

**規則**：任何要用 `position:sticky` 或 `position:fixed` 的新元件，動手寫 CSS 之前先自問：

1. 使用者捲動的時候，這個元素跟它下面/旁邊的內容是什麼視覺關係？畫一下（或用文字描述一遍）「捲到一半時，眼睛看到的畫面長怎樣」。
2. 如果這個元素跟多欄版面（`columns:`）或清單同時存在，它是「清楚地浮在上面、內容從它後面滑過」，還是「看起來像被插進清單中間」？如果答不出來哪一種，先別做 sticky。
3. 如果做 sticky，背景色一定要跟它所在容器的底色有能辨識的差異（同色系深淺至少要在截圖裡看得出來，不能只有 CSS 變數名字不同、實際顏色太接近）。加 `border-bottom` 或 `box-shadow` 幫忙製造分隔感，但不能只靠這個——顏色本身要先夠明顯。

**為什麼**：2026-09-16 索引頁的即時篩選框做成 sticky，捲動時使用者反應「看起來像被硬插進清單中間」。根因不是 CSS 寫錯（sticky 定位本身完全正確），是沒有先想過「這個元素跟底下兩欄式清單捲動時會呈現什麼畫面」就直接做了。後來試過加背景色加陰影還是不夠明顯（`--bg` 跟 `--side` 兩個深色系太接近，肉眼幾乎分不出來），最後判斷這個位置根本不適合做 sticky，直接拿掉，改成跟頁面一起捲動的一般元素。

**側欄/固定工具列類元件優先原則**：像側欄頂部的「全部/QA/後端/前端」篩選器這種，因為它**本來就在自己容器的最頂端**（沒有任何內容在它上面），sticky 起來只會有「內容從下方流過」這一種效果，不會有「插進中間」的疑慮，這是安全的 sticky 用法。反過來，如果一個元素的自然位置是在內容中間（像索引頁篩選框那樣夾在兩欄清單之間），做 sticky 幾乎注定會有這個問題——優先考慮不要 sticky，或把它移到真正的「容器頂端」位置。

## 改完之後

三類（連結／互動狀態／sticky）改到任何一類，跑一次：

```bash
node scripts/smoketest.js
```

全程走隔離的 port 與暫存 `progress.json`（見 `scripts/smoketest.js` 開頭註解），不會碰到真實紀錄。新發現的同類問題，順手在 `smoketest.js` 裡加一條對應檢查，不要只手動測一次就算了——參考檔案裡已有的「2026-09-16 曾經壞過」註解格式。
