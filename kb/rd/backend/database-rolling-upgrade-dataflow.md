## 定義
滾動升級是每次只把新版本部署到少數節點、確認正常再逐步推廣的發版方式，讓服務不中斷也能上線新版本。寫入資料庫可視為「給未來的自己傳送訊息」，因此資料庫寫入必須向後相容；同時滾動升級期間，新版本寫入的資料可能被還沒升級的舊版本讀到，因此也需要向前相容。

## 原理
資料比程式碼更長壽：五年前寫入的舊格式資料仍可能原封不動留在資料庫裡，除非顯式做資料遷移。大部分關聯式資料庫允許簡單的模式變更（如新增有預設值的欄位）而不必重寫既有資料；但把單值改多值、拆分資料到別的表這類複雜遷移，仍要在應用層自行處理，且如何做到雙向相容目前仍是開放問題。

## QA 視角
- 怎麼測：在測試環境模擬灰度發布，同時起新舊兩版服務指向同一份資料庫，交叉測試「舊版寫入→新版讀取」與「新版寫入→舊版讀取」，特別關注新增/刪除欄位、狀態機新增狀態值時舊版是否會誤判或崩潰。
- 常見缺陷：
  - 資料庫新增一個狀態值（如訂單狀態多一種），舊版程式碼的 switch/if 沒有 default 分支，直接當機或誤判成其他狀態
  - 遷移腳本只处理了新資料，五年前的舊格式資料在被讀到時觸發未預期的 null pointer 或型別錯誤
  - 灰度期間部分節點已升級、部分未升級，同一使用者兩次請求分別打到不同版本節點，行為不一致但難以復現（時好時壞）
  - 複雜遷移（欄位拆表）採用「雙寫」過渡期，忘記某條寫入路徑只寫了新表沒寫舊表，造成兩表資料不一致
