## 定義

watch（以及 effect 的排程機制）可以指定回呼函式何時執行：立即同步執行、或放進一個任務佇列，等目前這輪同步程式碼跑完（透過 `Promise.resolve().then(...)` 進入微任務）才批次執行。任務佇列用 Set 去重，同一個回呼在一輪同步程式碼內被觸發多次，最後只會實際執行一次。

## 原理

這個機制的目的是避免「資料改一次、回呼跑一次」造成的效能浪費：同一個巨集任務裡連續修改依賴多次（例如迴圈中連續 +1 十次），若每次都同步觸發回呼，會白跑九次沒有意義的中間態；批次到微任務佇列後，只在所有同步修改都結束後執行一次，讀到的是最終值。這代表回呼看到的「新值」不保證等於「觸發當下那一瞬間」的值，而是執行回呼那一刻的最新值。

## QA 視角
- 怎麼測：用程式或連續操作在同一個事件處理函式內連續修改被監聽的資料多次，確認監聽回呼（如自動儲存、聯動計算）只觸發一次而非每次修改都觸發一次。
- 怎麼測：確認畫面上「依賴監聽回呼才更新的內容」在同步程式碼執行完之後才出現，而不是操作當下立刻同步出現（若測試斷言下手太快、沒等一個 tick，可能誤判為「沒反應」）。
- 常見缺陷：測試腳本在觸發資料變更後立刻斷言畫面已更新，實際上要等下一個微任務/tick 才會反映，造成偶發性斷言失敗（flaky test），根因是測試沒等非同步更新完成而非功能壞了。
- 常見缺陷：同一批操作觸發多次監聽回呼，導致 API 被重複呼叫多次（如自動儲存打了 N 次而非 1 次），使用者看到重複的請求記錄或效能異常。
- 常見缺陷：`immediate` 類設定沒開啟時，頁面剛載入的初始狀態沒有跑過一次回呼，導致畫面初始顯示與資料實際狀態不一致，要等第一次資料變更才「補上」正確畫面。
